## 1. FR-07 元数据缓存

### 1.1 现状与问题

| 位置 | 现状 | 问题 |
|------|------|------|
| `internal/service/meta.go:23-37` | `Tables()` 每次 `driver.ListTables()` 直连业务库 | 无任何缓存，重复扫描 |
| `internal/service/meta.go:40-58` | `Columns()` 同理 | 换表就重扫 |
| `internal/api/meta_handler.go:22-34` | 无 `refresh` / `limit` 参数，无缓存命中信息 | 前端无法区分「缓存」与「新扫」 |
| `frontend/src/pages/Config.vue:749-767` | `loadTables(kw)` 每次关键词变化都打一次接口（`el-select` 的 `remote-method`） | 输入「STEEL」5 个字母 = 5 次全表扫描 |
| `frontend/src/pages/Config.vue:105-106` | 「刷新表清单」按钮调用 `loadTables('')` | 加缓存后此按钮会失去意义，必须带 `refresh=1` |
| `internal/datasource/driver.go:47-64` | `Driver` 接口无索引方法 | FR-07 的「索引清单浏览」⛔；也影响 FR-15 慢查询排查 |

**业务影响（实测场景）**：Oracle 生产库 `ALL_TABLES` 在几千张表的 schema 下约 0.8–2s，`ALL_TAB_COLUMNS` 约 0.3–1s。配置页每次输入表名关键字都要等 1s+，用户体验上等同于「卡死」。

### 1.2 目标与验收

- 同一数据源 5 分钟内重复拉表清单/字段清单 **不再访问业务库**（可从业务库侧 session 或日志确认）
- 表名关键字搜索变**纯内存过滤**，响应 < 50ms（前端输入无感）
- 点「刷新表清单」必定穿透缓存重新扫描
- 数据源被修改/删除/连接测试成功后，对应缓存**立即失效**
- 新增表索引清单查看能力

### 1.3 设计

#### 1.3.1 缓存结构（`internal/service/meta.go`）

```go
// TTL 内复用；同 key 并发只扫一次
type tableCacheEntry struct {
    items    []datasource.TableMeta
    loadedAt time.Time
}

type MetaService struct {
    ds       *DatasourceService
    ttl      time.Duration      // meta.cache_ttl_sec，默认 300s；<=0 关闭缓存
    limit    int                // meta.table_limit，默认 3000，防止超大 schema 撑爆响应
    mu       sync.RWMutex
    tables   map[int64]*tableCacheEntry              // key: datasourceID
    cols     map[string]*colCacheEntry               // key: "dsID|lower(table)"
    inflight map[string]*inflightCall                // 单飞：同 key 并发只扫一次
}
```

要点：
1. **表清单缓存按数据源整体缓存**（不是按 keyword），keyword 在内存里过滤。这样远程搜索零 IO。
2. **字段清单按「数据源 + 表名小写」缓存**（Oracle/MySQL 大小写不敏感，统一 lower 作 key）。
3. **单飞（single-flight）**：`inflight[key]` 存 `chan struct{}`，后到的请求 `<-ch` 等第一个扫完直接读缓存。防「打开下拉 + 同时点刷新」触发双扫。
4. **响应截断**：`limit` 生效时返回 `total`（真实条数）与 `truncated: true`，前端提示「共 N 张表，仅显示前 3000，请用关键字精确搜索」。过滤在截断前做，所以关键字搜索不受限制。
5. 缓存条目在 `len(items) == 0` 时**不写入**（避免一次失败的扫描把空结果缓存 5 分钟）。

#### 1.3.2 失效路径

`MetaService` 依赖 `DatasourceService`，反向不能直接调用（包内循环）。用回调注册：

```go
// service/datasource.go
func (s *DatasourceService) OnChange(fn func(datasourceID int64)) { s.hooks = append(s.hooks, fn) }

// cmd/server/main.go 装配
metaSvc := service.NewMetaService(dsSvc, cfg.Meta)
dsSvc.OnChange(metaSvc.Invalidate)
```

`DatasourceService` 的 Update / Delete / TestByID（测试成功即认为连接参数变了）/ TestInput 之后调 `hooks`。失效是**按数据源整体清空**（表 + 字段），实现简单且不会漏。

#### 1.3.3 接口变更（`internal/api/meta_handler.go`）

| 接口 | 变更 |
|------|------|
| `GET /api/datasources/:id/tables` | 新增 `keyword`（改为内存过滤）、`refresh=1`（强制重扫）、`limit`（覆盖默认上限）；响应由 `[]TableMeta` 改为对象 `{items, total, truncated, cached, ageSec}` |
| `GET /api/datasources/:id/tables/:name/columns` | 新增 `refresh=1`；响应改为 `{items, cached, ageSec}` |

#### 1.3.4 索引清单实现

`driver.go` 增加**可选接口**（不破坏现有 5 个驱动的实现）：

```go
type IndexMeta struct {
    Name    string   `json:"name"`
    Columns []string `json:"columns"`
    Unique  bool     `json:"unique"`
    Primary bool     `json:"primary"`
}

type IndexProvider interface {
    ListIndexes(ctx context.Context, db *sql.DB, table string) ([]IndexMeta, error)
}
```

各库取数来源：

| 库 | 系统视图 / 语句 |
|----|-----------------|
| MySQL | `information_schema.STATISTICS`（按 `SEQ_IN_INDEX` 排序还原列序） |
| PostgreSQL | `pg_index` + `pg_attribute` + `pg_class` |
| SQL Server | `sys.indexes` + `sys.index_columns` + `sys.columns` |
| Oracle | `ALL_INDEXES` + `ALL_IND_COLUMNS`（放在 `oracle_common.go`，两个驱动共用一份 SQL） |
| SQLite | `PRAGMA index_list` + `PRAGMA index_info` |

前端在「输出字段」区加一个「表结构 / 索引」抽屉（只读展示），顺便为 FR-15 的「索引提示」打基础。

### 1.5 风险与对策

| 风险 | 对策 |
|------|------|
| 缓存陈旧：DDL 新增表后 5 分钟内看不到 | 提供显式 `refresh=1`；数据源改动即失效；TTL 可配置（设为 0 即回到实时扫描） |
| 超大 schema 内存占用（3 万表 × 5 数据源 ≈ 15MB） | 单数据源上限 5 万条，超限截断并打 warn；表结构体很小（约 100 字节） |
| 响应截断导致用户找不到表 | 关键字过滤在内存全量上做，截断只影响"不搜索全览"场景，并明确提示 |
| `Invalidate` 漏调 → 改了数据源仍看到旧表 | 失效挂在 `DatasourceService` 的写入口内部（不是 handler 层），只有一处收敛 |

## 2. FR-11 表生成报表

### 2.1 现状与问题

现在的能力是 `frontend/src/pages/Config.vue:92-134` 的**内嵌流程**：选表 → 勾字段 → `applyPick()`（`Config.vue:800-818`）拼一段 `SELECT col1, col2 FROM t`，然后合并展示列。

| 缺口 | 说明 |
|------|------|
| 无排序 | 生成的 SQL 没有 `ORDER BY`。Oracle 下分页无排序时结果可能跨页重复/漏行——这是**真实的数据正确性问题** |
| 无别名/去重 | 无法给结果列起别名，无法 `DISTINCT` |
| 无参数草稿 | 只生成查询主体，查询条件全靠手写 |
| 无校验 | 生成完直接写进 SQL 编辑器，字段名非法/表名跨模式等问题要等到预览才暴露 |
| 无独立入口 | 入口在配置页里、藏在「选表」模式中，新用户不易发现 |
| 生成逻辑在前端 | 引号处理、跨模式表名等规则无法复用后端已有的 `ValidateTableRef` / `QuoteIdentifier` |

### 2.2 目标

1. 报表中心一键进入「从表建报表」向导，三步完成，最终得到一张**草稿状态的报表**
2. SQL 生成规则收敛到后端一处，规则可测、可复用
3. 生成的 SQL 默认带排序（保证分页稳定）、参数名/中文列名按既有解耦规则处理
4. 生成结果可预览（复用现有 `/api/reports/:id/preview` 需要先落库 → 因此向导期间提供**只读校验**，不落库）

### 2.3 设计

#### 2.3.1 后端：统一 SQL 生成器（新文件 `internal/service/report_wizard.go`）

```go
type WizardColumn struct {
    Name  string `json:"name"`  // 物理列名（必填，允许中文）
    Alias string `json:"alias"` // 结果列别名，空 = 同 Name
    Label string `json:"label"` // 展示名，空 = 字段注释 → 列名
}

type WizardReq struct {
    DatasourceID int64          `json:"datasourceId"`
    Table        string         `json:"table"`      // 支持「模式.表名」
    Columns      []WizardColumn `json:"columns"`
    Distinct     bool           `json:"distinct"`
    OrderBy      []WizardColumn `json:"orderBy"`    // 空 → 自动取主键
    WithParams   bool           `json:"withParams"` // 是否生成条件草稿
}

type WizardResp struct {
    SQLText  string         `json:"sqlText"`
    Columns  []ReportColumn `json:"columns"`
    Params   []ReportParam  `json:"params"`
    Warnings []string       `json:"warnings"`
}
```

**生成规则（逐条明确，便于评审）**：

1. **标识符引用**：名字匹配 `^[A-Za-z_][A-Za-z0-9_$#]*$` 时裸写；含中文/空格/特殊字符时用 `driver.QuoteIdentifier()` 包裹。
   - Oracle 中文列名加双引号安全（中文无大小写，引号前后等价）；不加引号则遇到保留字会报错。
2. **表名**：先过 `datasource.ValidateTableRef()`（既有能力，支持 `FGPESE0.SYS_DICT_TYPE`），非法直接报错，不让非法串进 SQL。
3. **`DISTINCT`**：`SELECT DISTINCT` 前缀。
4. **别名**：`COL AS "别名"`；设了别名时**结果列名 = 别名**，`ReportColumn.ColName` 必须与之一致，否则查询结果回填展示列会错位。
5. **`ORDER BY`**：用户选的字段（可多选，带 asc/desc）；未选时若表有主键 → 自动 `ORDER BY 主键`；无主键 → 不生成并给出 warning：
   > 「该表未检测到主键，建议指定排序字段，否则分页时结果顺序不稳定」
6. **不生成 `LIMIT` / `ROWNUM`**：分页由查询引擎接管（`Paginate` 已按 Oracle 版本分 12c `OFFSET/FETCH` 与 11g 三层 `ROWNUM`）。向导里生成 LIMIT 会与引擎二次分页冲突。
7. **参数草稿（`withParams`）**：

   | 列特征 | 生成条件 | 参数名 / 列名 |
   |--------|----------|---------------|
   | 主键列 | `AND T.PK = :condN` | `cond1` / 列名 |
   | 列名含 `NO`/`CODE`/`NAME`/`_ID` | 字符串等值（可勾选改为 LIKE） | 同上 |
   | 日期/时间类型 | 暂不生成（区间条件留 P2），仅在 `Warnings` 里提示「可手动加时间范围」 | — |

   严格复用 `01-开发文档` 里已定的规则：**参数名只能是英文标识符（`cond1`），列名可以中文（写进 `columnName`，自动装配时用引号包裹）**。中文列名绝不能直接当参数名——这是之前踩过的错。

8. **输出 `ReportColumn`**：`colName` = 别名或原名，`label` = 用户填的 label → 字段注释（`trim()` 后非空）→ 列名，`sortNo` 按勾选顺序。

#### 2.3.2 接口

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| `POST` | `/api/reports/wizard/generate` | `report:create` | 传入 `WizardReq`，返回 `WizardResp`，**只生成不落库** |

**为什么不做「一键建库」接口**：写入已有唯一入口 `POST /api/reports`（含权限、审计、分组授权默认值等逻辑）。再开一条写库路径会产生两套校验，后续改报表模型必然漏改一处。向导只负责「生成草稿」，前端拿到后走现有保存接口即可——失败时用户还能回到向导调，不会留下半张报表。

#### 2.3.3 前端：三步向导（新组件 `frontend/src/components/ReportWizard.vue`）

入口：`Reports.vue` 工具栏「从表建报表」按钮（`can('report:create')` 时显示），打开 `el-dialog`（宽度 900，`destroy-on-close`）：

**第 1 步 选表**
- 数据源下拉（复用 `/api/datasources`）
- 表下拉：`filterable remote`，接 FR-07 的缓存接口（**依赖 FR-07 先做**，否则这里会成为新的卡顿点）
- 选中表后展示：表注释、字段数、主键

**第 2 步 选字段**
- 字段列表：勾选 + 搜索 + 全选；展示 `字段名 / 类型 / 注释 / PK 标记`
- 每行可填「别名」「显示名」，默认显示名 = 注释
- 顶部开关：`DISTINCT`
- 底部排序区：「排序字段」多选（从已勾选字段中选）+ 升降序

**第 3 步 预览与确认**
- 展示后端返回的 `sqlText`（只读代码块，等宽字体）、生成的条件草稿表格、`warnings` 列表
- 报表基本信息：名称（默认 `表注释 + 列表`）、分组
- 「创建草稿报表」→ 组装成 `POST /api/reports` 的 payload → 成功后关闭向导、`router.push('/config?id=' + id)` 继续精调展示列/字典翻译

**与现有内嵌流程的关系**：并存。配置页里的「选表」模式仍保留（手写 SQL 场景下临时插一段表名/字段名很方便），但把 `applyPick()` 改为调用同一个后端生成器，消除前后端两套拼串逻辑——这是本次的附加收益。

### 2.5 风险与对策

| 风险 | 对策 |
|------|------|
| 生成的 SQL 在目标库跑不通（保留字、大小写敏感列名） | 生成后提供「试跑校验」按钮（用已发布/草稿报表的 preview 需要 id，故改为**建本地草稿后再预览**；向导请求里带 `validate=true` 时后端只做 `EXPLAIN`/`SELECT ... WHERE 1=0` 试探，不返回数据） |
| 表很大，向导里的字段元数据请求慢 | 依赖 FR-07 缓存 |
| 用户勾了上千个字段生成超长 SQL | 硬上限 2000 列（高于 Oracle 1000 / PG 1664 / SQLite 2000 的单表列数），不拦正常宽表；另设 SQL 60KB 上限对应 MySQL `TEXT`，超出提示「减少字段或缩短别名」而不是让保存时报 Data too long |
| 宽表在向导里渲染卡顿 | 字段表格按 100 行/页分页（`el-table` 无虚拟滚动，一次渲染上千行会明显卡住） |
| 别名重复导致结果列重名 | 后端校验别名唯一性，重复直接报错 |

> `validate` 属于 P2 增强，v1 先靠「创建后立刻预览」发现 SQL 问题（成本更低）。方案评审时可按需要提升优先级。

### 3.2 目标

1. 日志写入不再「一条一 goroutine」，改为有界队列 + 批量落库，队列满时降级丢日志并计数（优先保业务响应）
2. 保留期自动清理生效（`log.audit_retention_days`，默认 90 天，≤0 关闭）
3. 管理员可在页面上按类型/用户/时间/结果筛选查询、看详情、导出 CSV、手动清理
4. 老库升级后自动出现「操作日志」菜单（不需要手工建菜单）

### 3.3 设计

#### 3.3.1 写入侧：有界队列 + 批量

```go
type AuditService struct {
    db      *gorm.DB
    ch      chan AuditEntry
    dropped int64 // atomic
    syncW   bool  // log.audit_sync=true 时退回同步写（排障用）
}

func (s *AuditService) Start()  // 启动 1 个 worker
func (s *AuditService) Close()  // 关闭前 flush 剩余
```

- 队列容量 2048；worker 单协程，**攒 200 条或 1 秒**做一次 `CreateInBatches(batch, 100)`
- 满队列时 `select default:` 丢弃 + `atomic.AddInt64(&dropped, 1)`；每 60s 打一条 warn：`[audit] 队列已满，近 1 分钟丢弃 N 条日志`
- `main.go` 里 `auditSvc.Start()` + `defer auditSvc.Close()`（`router.Run` 返回后 flush）
- 保留 `LogAsync` 方法名不变，内部改投递 channel → **所有调用方零改动**

> 为什么单 worker 而不是多 worker：SQLite 是单写者，多 worker 只会增加 `SQLITE_BUSY` 重试。MySQL 模式下如果日志量大，把 `workers` 做成配置项即可（默认 1）。

#### 3.3.2 模型补强（`internal/model/model.go`）

| 新字段 | 类型 | 默认值 | 用途 |
|--------|------|--------|------|
| `Module` | `size:32;default:''` | '' | report / datasource / dict / system / export |
| `Target` | `size:128;default:''` | '' | 目标名称快照（报表名、数据源名），对象删除后日志仍可读 |
| `UserAgent` | `size:255;default:''` | '' | 浏览器/客户端 |
| `TraceID` | `size:36;default:''` | '' | 同一请求串联（Gin 中间件生成） |
| `ErrMsg` | `size:255;default:''` | '' | 失败原因摘要 |

> **必须带 `default:''`**：SQLite 不允许给已有表加「NOT NULL 且无默认值」的列，`main.go:46-48` 已有该报错提示。AutoMigrate 增量加列在三种系统库下均安全。
>
> 新增复合索引：`idx_audit_type_created (log_type, created_at)`，配合已有的 `created_at` 索引支撑按类型+时间筛选。

#### 3.3.3 查询/导出/清理接口（新文件 `internal/api/audit_handler.go`）

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| `GET` | `/api/system/audit-logs` | `system:audit:list` | 参数：`logType, username, keyword(Detail/Target), success, reportId, datasourceId, from, to, page, pageSize`（`pageSize` 上限 200） |
| `GET` | `/api/system/audit-logs/stats` | `system:audit:list` | `?days=7`：按类型计数、失败数、Top5 用户/Top5 报表（P2，供后续仪表盘） |
| `GET` | `/api/system/audit-logs/export` | `system:audit:export` | 同筛选条件流式导出 CSV，上限 10 万行 |
| `DELETE` | `/api/system/audit-logs` | `system:audit:delete` | `?before=YYYY-MM-DD`，删除该日期之前的日志，返回删除行数 |

`from`/`to` 接受 `2006-01-02` 或 `2006-01-02 15:04:05`；`to` 按「当天 23:59:59」处理（含当天）。所有时间按服务器本地时区。

#### 3.3.4 自动清理（`AuditService.StartCleanup(days int)`）

复用导出清理的成熟模式（`export.go:457-478`）：

```go
func (s *AuditService) StartCleanup(days int) {
    if days <= 0 { log.Println("[audit] 保留期未配置，自动清理关闭"); return }
    go func() {
        for {
            s.cleanupOnce(days)
            time.Sleep(6 * time.Hour)
        }
    }()
}
```

`cleanupOnce` 分批删（每批 5000 行，循环到 0）：**先 `SELECT id ... LIMIT 5000`，再 `DELETE WHERE id IN (...)`**。不用 `DELETE ... LIMIT`——SQLite 默认编译选项不支持，MySQL/PG 语法也不同。

启动时立即执行一次（不只是等 6 小时），便于运维「改小保留期 → 重启 → 立刻生效」。

```go
// ensureExtraMenus 幂等补齐后续版本新增的菜单/权限点（已存在则跳过）
func ensureExtraMenus(db *gorm.DB) error {
    for _, m := range extraMenus() {
        var cnt int64
        db.Model(&model.Menu{}).Where("id = ? OR (perms <> '' AND perms = ?)", m.ID, m.Perms).Count(&cnt)
        if cnt == 0 { db.Create(&m) }
    }
    return nil
}
```

用 `ID 或 perms` 双条件判断，避免与用户手工建的菜单 ID 撞车。`admin` 是隐式通配 `*`，无需授权即可看到；其他角色由管理员在角色管理页勾选。

### 3.5 风险与对策

| 风险 | 对策 |
|------|------|
| 队列满丢日志 | 明确「业务优先」取舍；丢弃计数暴露在 `/api/health` 的 `auditDropped` 字段，可监控；`log.audit_sync=true` 可切回同步写排障 |
| 进程被 kill -9 时队列内日志丢失 | 只影响最后 ≤1 秒的日志；systemd 用 `SIGTERM` 正常停止即可 flush |
| 老库 AutoMigrate 加 NOT NULL 列失败 | 新字段全部带 `default:''`；`main.go:46-48` 已有可读报错 |
| 清理误删近期日志 | 只删 `created_at < cutoff`；手动清理需二次确认；`days<=0` 直接关闭自动清理 |
| 大表 COUNT 慢 | `pageSize` 上限 200；筛选优先命中 `idx_audit_type_created`；`COUNT` 超时可降级为「总数未知」（可选，参照查询引擎已有做法） |

## 6. 明确不做（本次范围外）

| 项 | 原因 |
|----|------|
| 元数据缓存持久化到系统库 | 进程内 TTL 已够用；落库会引入「DB 里存的表结构早于真实库」的新问题 |
| 多表关联（JOIN）向导 | 复杂度陡增（别名、字段歧义、聚合），单人日量级撑不住；先用 SQL 编辑器 |
| 日志实时推送（WebSocket） | 查询/刷新足够；无并发观看需求 |
| 审计日志分库/归档到文件 | 单机部署场景下 90 天保留期已控制体积 |
| 列配置变更埋点 | 高频低价值，会产生大量噪音日志 |
